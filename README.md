# Monitrail

A lightweight uptime and performance monitoring platform for websites and web services. Monitor availability, track response times, detect incidents, and receive alerts when services go down or recover.

This project is licensed under [MIT](LICENSE). Hosted signups remain
invite-only through dogfood. Production acceptance and the ongoing proof
milestone are tracked in the [Phase 11 verification log](docs/phase-11-verification.md).

Read [AGENTS.md](AGENTS.md), then docs 01–07 in order before contributing.
The [implementation plan](docs/06-implementation-plan.md) tracks current
work. Phases 0–3 established the initial workspaces, database, OAuth,
owner-scoped access and SSRF guard. Phase 3b aligns those foundations with
the revised specifications. The [delta report](docs/phase-3b-delta-report.md)
records the approved scope.

## Local setup

Use Node.js 24.12.0 (`.nvmrc`) and npm 11.6.2. Install the pinned workspace
dependencies from the repository root:

```sh
npm ci
```

The root lockfile serves both packages; do not create package-level lockfiles.
`web/` is the Next.js App Router app, `checker/` is the Cloudflare Worker,
and `shared/` contains security code used by both workspaces.

Run from the root:

```sh
npm run dev --workspace web
npm run dev --workspace checker
npm run build
npm run lint
npm run typecheck
npm test
npm run test:runtime --workspace checker
```

Both packages also expose `build`, `lint`, `typecheck` and `test` scripts
that can be run from their own directories. The Worker build is a local
Wrangler dry run, not a deployment. Its runtime types are generated by
`npm run typecheck`. The web typecheck generates Next.js route types first.
Biome supplies the shared recommended lint rules and React/Next.js rules
for the web app. TypeScript checks run separately.
The web scripts use Next.js's supported Webpack mode because Turbopack's
PostCSS subprocess could not bind its required local port in this environment.

Web Vitest tests apply the committed SQL migrations to in-memory PostgreSQL
(PGlite) and exercise ownership, OAuth/session security, durable auth limiting,
cascade deletion, incident uniqueness and seed safety. These tests need no
credentials and never connect to `DATABASE_URL`. Checker tests cover SSRF
static policy, redirects and request limits. The separate workerd test uses an
offline fixture Worker to exercise native fetch and byte streams.
Playwright supplies browser smoke tooling for later application flows.

## Environment and scope

Each package has a names-only `.env.example`. It is an inventory, not a
ready-to-use dotenv file: when a later phase needs credentials, create an
ignored `web/.env.local` or `checker/.dev.vars` and provide only the needed
`NAME=value` entries. Phase 0 builds and runs without credentials. Never
commit or print secret values.

The web app includes a landing page, OAuth login, and a protected workspace
for creating, editing, pausing, resuming and deleting monitors.
The checker runs on a one-minute schedule through a private Cloudflare
Queue. Create `monitrail-check-ticks` in the target Cloudflare account
before deploying the checker. The consumer uses `APP_URL` and
`INTERNAL_HMAC_SECRET` to claim work and submit results through the signed
web API. See the [Phase 5 verification log](docs/phase-5-verification.md)
for staging evidence and the deployment gates.
Database lifecycle commands are administrative scripts. The server-only auth
persistence boundary and application DAL are separate. The SSRF guard is
used for monitor URL validation. See the [Phase 4 verification log](docs/phase-4-verification.md).
Phase 11 covers production deployment and public source release.

Tool telemetry is disabled in Next.js dev/build/start and Wrangler scripts.
The local Git identity is the project alias `Monitrail <dev@monitrail.invalid>`.
The address uses the reserved `.invalid` domain.

See `docs/phase-0-verification.md` for dependency decisions, provider checks,
verification results and unresolved decisions for subsequent phases.

## Alert configuration

Provide `CHANNEL_ENC_KEY_ID` and `CHANNEL_ENC_KEY` to the web runtime. The
key is 32 random bytes encoded as unpadded base64url. Use the same active key
across all runtime instances. To enable Telegram linking, configure the bot
token, bot username and a randomly generated webhook secret of 32–256
URL-safe characters. Register the
bot’s HTTPS webhook at `/api/telegram/webhook` with that secret and restrict
updates to `message`. [Telegram webhook setup](https://core.telegram.org/bots/api#setwebhook)

To rotate the channel key, deploy the new key as the previous key first so
all readers can use both. Then switch the active and previous key pairs.
After old writers have drained, supply the keys and both database URLs to
the administrator process and run:

```sh
npm run alerts:rotate-keys --workspace web -- --confirm-rotate-channel-keys
```

Retire the previous key after rotation and after requests that could have
read an old envelope have drained.

## Database development

The active Drizzle schema and SQL migrations are in
`web/src/db/rev2-schema.ts` and `web/drizzle-rev2/`. Use a fresh,
disposable Supabase project with the Data API disabled. The original Neon
migration track is retained for the historical Phase 1 evidence.

For local setup, put the Transaction pooler URL in `DATABASE_URL` and the
Session pooler or Direct URL in `MIGRATION_DATABASE_URL` in the ignored
`web/.env.phase3b.local`. Download the Supabase CA from the dashboard to
`web/.certs/supabase-ca.crt`. To use another certificate path, set
`DATABASE_CA_FILE`. See [Supabase connection modes](https://supabase.com/docs/guides/database/connecting-to-postgres)
and [SSL verification](https://supabase.com/docs/guides/platform/ssl-enforcement).

On the fresh test project, run:

```sh
npm run db:verify-postgres --workspace web
```

This command checks both TLS connections, applies and replays the committed
migration, seeds two synthetic owners with paused monitors and unpublished
pages, then creates and verifies the restricted runtime role. It replaces
the local runtime URL with that role's credential. Keep the administrative
URL in the ignored local file and use only the restricted connection in
the hosted web app. Keep connection strings out of commands, logs and Git.

Use `npm run db:generate --workspace web` to generate migrations offline.
The separate `db:migrate` and `db:seed` commands use the configured admin
connection. Run the seed only on development fixtures.

## Authentication development

Set `APP_URL=http://localhost:3000`, provider client IDs/secrets under the
`AUTH_GITHUB_*` and `AUTH_GOOGLE_*` names, and `SIGNUP_MODE=invite`
in ignored `web/.env.local`. Provider callbacks are
`http://localhost:3000/api/auth/callback/github` and
`http://localhost:3000/api/auth/callback/google`. Use the same origin in the
browser; the dev/start scripts bind to loopback `localhost`.

```sh
npm run auth:prepare --workspace web -- --generate-missing-secret
npm run dev --workspace web
```

Preparation validates settings, generates `AUTH_SECRET` only when missing,
restricts local-file permissions and never displays values. Production requires
an HTTPS `APP_URL` and matching provider registrations. Accounts are keyed
by provider and provider account ID. Email may be absent. A second provider
with an already registered email receives a message to use the original
provider.

To invite a new user in the disposable development environment, run
`npm run auth:invite --workspace web`. Open `web/.env.invite.local` locally
for the single-use code. Remove that ignored file after using the code
before creating another invite.

With the dev server running and the synthetic Supabase fixture owners present:

```sh
npm run auth:verify-local --workspace web -- --confirm-fixture-session
npm run auth:verify-secrets --workspace web
```

To check the production build over local HTTPS, with installed Chromium and
OpenSSL available:

```sh
npm run build
npm run auth:verify-production --workspace web -- --confirm-fixture-session
```

This starts a loopback-only test server and temporary TLS proxy, validates
secure cookies and no-JavaScript content, then removes its temporary session,
certificate/key and test processes. Real provider credentials stay in process;
no provider requests are made by this test.

The browser acceptance creates only a temporary session for a known fake
fixture identity, tests access/ownership/layout/logout, and removes that
session. It makes no provider or monitored-target requests. Real provider
consent must be tested separately by an account owner. The credential scanner
privately compares configured values with Git-eligible files and browser assets.
See the [Phase 3b verification log](docs/phase-3b-verification.md) for evidence and remaining checks.

## Maintenance and health

The Worker calls signed maintenance daily at 03:17 UTC. Maintenance removes
expired data, validates monitor DNS, and logs table sizes and an 80% storage
warning. Unsafe or failed DNS validation pauses the affected monitor.
Save a URL that passes validation, then resume it.

`GET /api/health` has an empty response and returns 503 when checker updates
are at least three minutes old, storage reaches 450,000,000 bytes, or the
measurement fails. Run the independent probe with `APP_URL` set to the
deployed HTTPS origin.

```sh
node scripts/check-health.mjs
node --test scripts/check-health.test.mjs
```

At deployment, set the GitHub repository variable `APP_URL`, merge the
health workflow onto the default branch, and enable Actions failure
notifications. Its schedule runs every 15 minutes. Scheduled jobs wait for
`APP_URL` to be configured. Manual runs report missing configuration as a
failure. GitHub can delay scheduled runs. Standard public-repository
runners are free, while private-repository runs consume the plan's compute
allowance. [GitHub scheduling](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule),
[GitHub Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions).

## Security and production verification

```sh
npm run lint
npm run build
npm run typecheck
npm test
npm run security:scan
npm run test:production
```

Production verification uses an isolated local PostgreSQL database and
synthetic accounts. It exercises keyboard journeys, ownership checks,
public cache revocation, account deletion, Lighthouse audits and the
storage benchmark. It requires OpenSSL, PostgreSQL binaries under
`/usr/lib/postgresql`, and Chromium. It uses a system Chromium when
available, or the browser installed by the pinned Playwright package.
Reports go to a temporary directory or `QA_REPORT_DIR`.

The browser test intercepts the OAuth authorization page and represents
Telegram's Start action through its authenticated incoming webhook.
Live provider consent is verified by the account owner.

The CI workflow runs these checks on main and pull requests with synthetic
configuration. Source and history scanning uses checksum-verified Gitleaks
8.30.1. Lighthouse 13.6.0 is a pinned development dependency.

HTML uses a fresh CSP nonce and no-store caching. Scripts and style
elements require the nonce. Style attributes remain enabled for Recharts.
Management writes share the approved 60-per-hour owner budget. Account
deletion has a separate three-attempt budget.

Set `ABUSE_CONTACT_EMAIL` to an alias address you own before deployment.
The production `/bot` page requires a valid contact address.
